# 2006/meyer

Difficulty: Medium

1. Hand-made objects with a shared virtual method table

Every "class" is a struct whose first field `M` points into one global array
of function pointers, `K M[17]`. `L[4]` holds the starting point of each
class's slice of that array: the board `F` starts at `M+0`, the abstract
player `G` at `M+5`, the human `H` at `M+9` and the computer `I` at `M+13`.
A call like `((F3)_->M[3])(_, p, q, r)` means "call method number 3 of this
object", so you have to count entries in the table to find out that it is
really the board's "is this move legal" function. The rewrite calls plain
functions directly and keeps a single `choose_move` function pointer for the
two kinds of player.

2. Function pointer casts to hide signatures

All methods are stored as the generic type `void (*)(void)` and cast back to
the right type at the call site with typedefs like `F1`, `F3`, `G2`. The type
name says nothing about what the function does, only which class and slot it
belongs to.

3. Look-alike function names

The methods are called `OOOO`, `OOOl`, `OOlO`, `OOll`, `OlOO`, `OlOl`, `OllO`,
`Olll`, `lOOO`, `lOOl`, `lOlO`, `lOll`, which mix the letters `O` and `l`
so they look like `0` and `1` and are very hard to tell apart. Even the null
table entries are written `(K)0000` to blend in.

4. Constructors generated by token pasting

The macros `h`, `i` and `j` use `##` to build functions `NF`, `NG`, `NH` and
`NI` ("new F", "new H" and so on). Each one mallocs the object, looks up its
table with `L[J##p]` (the `JF`..`JI` defines), and calls slot 0 as the
constructor. The derived constructors `Olll` and `lOOl` first call the base
constructor `lOll` and then overwrite its message, like inheritance.

5. Keyword and type aliases

`n`, `o`, `A`, `B`, `C`, `U` stand for `void`, `int`, `char`, `const`,
`typedef` and `return`, and `D`/`E` combine them into `typedef void` and
`typedef int`. The macro `k` builds a struct typedef that always starts with
the method table pointer.

6. Nested loops squashed into one `for`

Macros `a`, `b`, `d` and `e` turn two or three nested loops into a single
`for` whose step expression uses `?:` and commas to wrap the inner counter
and bump the outer one, like an odometer. `e(p,0,9,q,0,9,r,1,10)` is really
"for each value 1..9, for each row, for each column". The board printer
`OlOO` does the same thing and also prints the row label from inside the
step expression.

7. One string table with numeric offsets

All text lives in one string `O` separated by `\0`, and is used through
`printf(O+42)`, `scanf(O+48, ...)` and so on. You have to count characters to
see that `O+34` is `"you win"`, `O+58` is `"you lose"` and `O+6` is an empty
string. The macro `l(p)` hides that it is `printf(O+p`.

8. Packed board indexing

The board is a flat `int P[256]` and the macro `m(p,q)` computes
`(P + (q<<4 & 0360))[017 & p]`, i.e. row `q` times 16 plus column `p`, written
with shifts, octal masks and pointer indexing. The parameters are in column,
row order, opposite of how the player types them. The rewrite uses a normal
`cell[row][col]` array.

9. Bit-packed move list

The computer stores each candidate move as one int:
`s | (t << 5) | (u << 10)`, and later unpacks it with the masks `0x1f`,
`0x3e0` and `0x7c00`. The list size `01331` is octal for 729 (9*9*9).

10. Recursive `main` for argument handling

`main` calls itself with one fewer argument after each `srand(atoi(...))`,
so every argument seeds the generator in turn and the first one wins. This
is the same as seeding once with `argv[1]`.

11. Bit tricks for the turn counter

The player index starts as `42 & 1` (0), and the loop uses `p++` followed by
`p &= 5` to flip between 0 and 1. Setting `p = 4` ends the game because
`4+1 = 5` and `5 & 5 = 5` still has the 4 bit set, which stops `!(p&4)`.

12. Strange `goto` into a block

In `OOll` the label `v:` sits inside the `if` block, and the code after the
block jumps back into it with `goto v` just to `return u` (which is 0). This
makes it look like the function can fall off its end.
